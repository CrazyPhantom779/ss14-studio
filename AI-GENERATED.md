# AI-generated project disclosure

**SS14 Studio is an AI-generated, human-reviewed open-source project.**

This repository is developed with AI coding agents. The agents write code, tests,
documentation and UI copy under the direction of human maintainers. The project is
published openly so that every line can be inspected, reproduced and improved.

This file explains what that means in practice, where the project is labelled, what
the known limitations are, and what we ask of users and contributors.

## Scope of AI assistance

AI assistance has been used across the whole project, including:

- the framework-agnostic parser, validator, editor, inheritance resolver and
  graph algorithms in `packages/core`;
- the shared React interface in `packages/ui`, including the graph canvas,
  prototype explorer, RSI studio, XAML studio, diff view and settings;
- the VS Code extension host, indexer, webview panel, code lenses and tree views
  in `apps/vscode`;
- the Rider Kotlin host, Node sidecar, JCEF bridge and build scripts in
  `apps/rider`;
- tests, build configuration, CI, packaging and this documentation.

Most of the source in this repository was produced by AI agents. It is not a
small autocomplete assist on top of a hand-written codebase.

## Human review

Human maintainers review AI output before it is merged. Review includes reading
the change, running typechecks and tests, building the extension and Rider
plugin, and smoke-testing the sidecar against a real Space Station 14 repository.

Review is not a line-by-line audit of every generated statement. AI-assisted code
can contain subtle mistakes that compile and pass the current tests. Treat this
project like any other alpha software: read the code before trusting it in a
production pipeline, and report anything that looks wrong.

## Where the project is labelled

The AI-generated status is visible everywhere the project is distributed:

- this file and the banner at the top of the root `README.md`;
- the AI-generated badge in the README and the VS Code marketplace copy;
- the plugin description in the Rider plugin manifest;
- the **About & AI Disclosure** panel inside the extension, reachable from the
  command palette and the dashboard.

There is no attempt to hide the disclosure behind a link that users will never
open. The About panel is part of the product, not a legal afterthought.

## No watermark policy

SS14 Studio does **not** add an AI watermark, badge or permanent comment to your
prototypes, YAML, XAML, sprites or other project files.

The only marker the tool ever writes is the standard functional marker used by
RobustToolbox code generation:

```xml
<!-- AutoGenerated by SS14 Studio. This file may be regenerated. -->
```

That comment exists so that humans and tooling know a XAML file is generated and
may be replaced. It is not an AI watermark, and it is only added when you run the
**Mark XAML as AutoGenerated** command or when a generation flow explicitly asks
for it. You can remove it at any time with **Remove AutoGenerated Marker**.

Edits to YAML prototypes are surgical AST edits. They preserve comments,
formatting and ordering, and they are undoable with the editor's normal undo
command.

## Known limitations

SS14 Studio is alpha software. The following limitations are known and should be
considered when evaluating AI-generated output:

### General

- Large repositories take a few seconds to index. The first index of a full
  Space Station 14 fork can be several thousand prototype files.
- The extension and the Rider plugin share the same UI. A feature that is
  available in one host may be exposed through different integration points in
  the other.
- The Rider plugin has been compiled, packaged and exercised through its Node
  sidecar, but its JCEF runtime has not been verified on a local Rider
  installation. Rider developers should test the packaged ZIP before relying on
  it. See `apps/rider/README.md`.
- There is no telemetry, account system or hidden network access. The Rider
  sidecar binds to `127.0.0.1` and serves the UI and API on a loopback port.

### Construction graphs

- Graph display is a blueprint-style approximation, not a screenshot of the
  in-game construction menu.
- The parser understands the construction graph schema used by the projects we
  test against. A fork with custom YAML tags or unusual node shapes may produce
  incomplete views or informational diagnostics.
- Layout positions are stored in workspace state, not in YAML. They are local to
  your editor and are not committed with the graph.

### Prototypes

- The "in-game card" is an approximate inspector card built from prototype data.
  It is not a running engine and does not simulate every component.
- Inheritance resolution follows RobustToolbox semantics for multiple parents,
  component merging and partial overlays. Sequence-level `!Index` and
  `!CombineIndex` resolution is intentionally approximate: the UI shows the
  declared overlay and its provenance, not a full engine replay of every
  sequence operation.
- Partial prototypes are resolved from the configured partial directories. A
  project that declares partials through a non-standard mechanism may need its
  manifest added or its partials will appear as ordinary prototypes.

### XAML

- The visual designer is approximate. It renders a best-effort layout from
  RobustToolbox controls, styles and common properties. It is not engine-accurate
  and should not be used as a pixel-perfect preview.
- Validation covers structural XML problems, unknown controls, duplicate names,
  missing code-behind handlers and common RobustToolbox mistakes. It is not a
  full C# compiler or a complete schema for every control.
- Formatting and cleanup are conservative, but they still rewrite text. Review
  the before/after diff before saving, especially in files with unusual
  whitespace or comments.

### RSI sprites

- Adding or removing frames updates `meta.json` only. The sheet image is not
  regenerated automatically. Use **Replace PNG** or the pixel editor to change
  the sheet, then update the metadata to match.
- The pixel editor is a basic RGBA editor for quick fixes, not a replacement for
  Aseprite, Krita or a dedicated sprite pipeline.
- Non-atlas RSI layouts and `.rsic` compression are supported in metadata and
  loading. The editor does not recompress `.rsic` files.
- License and copyright fields are displayed and editable, but SS14 Studio does
  not verify that a sprite is legally reusable. That remains your responsibility.

### Diff and merge

- Diff views are read-only. SS14 Studio never applies a merge automatically.
- Merge-conflict detection looks for standard conflict markers. It does not
  replace a proper three-way merge tool.

## What we ask of users

1. **Review AI-assisted output before shipping it.** This applies to code
   changes, generated XAML, extracted partials and sprite edits.
2. **Report problems.** Open an issue at
   <https://github.com/CrazyPhantom779/ss14-studio/issues> with the file, a minimal
   reproduction and the version shown in the About panel.
3. **Do not assume engine parity.** If a visual result matters, verify it in the
   game client or in RobustToolbox tooling.
4. **Keep the disclosure intact.** Forks and redistributions should keep the AI
   disclosure, the About panel text and this file. Removing the label does not
   make the code hand-written.
